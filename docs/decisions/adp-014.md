# ADP-014 — Perfil Embedded, Arquitetura Dual-Track (Wasm Web vs VM Nativa) e Roteiro de Evolução da `aipo-vm`

- **Status**: Proposto (Em Discussão e Desenho Arquitetural)
- **Data**: 2026-10-06
- **Decisores**: Raillen & Poppy Team
- **Fase**: Planejamento Arquitetural / Evolução de Runtimes

---

## 1. Contexto e Motivação

Na decisão arquitetural **ADP-013**, a linguagem Aipo adotou o formato WebAssembly (Wasm 2.0 / WASI) e o engine Wasmtime (JIT Cranelift) como substrato principal para unificar a execução e pavimentar o auto-hospedamento (*self-hosting*).

Entretanto, medições empíricas e o alinhamento com a visão de longo prazo da linguagem revelaram requisitos que um motor JIT pesado como o Wasmtime não consegue suprir:

1. **Pegada de Memória e Tamanho de Binário**: O Wasmtime, ao incorporar o backend Cranelift, montadores x86/ARM, tabelas de desbobinamento de pilha e alocador de registradores, adiciona mais de 25 MB ao executável da CLI.
2. **Tempo de Inicialização (*Cold Start*) Incompatível com Shell**: Scripts de terminal, automações de infraestrutura e shells interativas exigem inicialização imediata (< 2 ms). A compilação e validação JIT do Wasmtime impõe uma sobretaxa inicial perceptível (15 ms a 50 ms).
3. **Inviabilidade em Microcontroladores (MCUs)**: Dispositivos sem MMU (ex.: Cortex-M, ESP32, RP2040) possuem tipicamente de 64 KB a 512 KB de Flash e de 16 KB a 64 KB de RAM estática. Eles são incapazes de executar runtimes JIT ou páginas executáveis dinâmicas (`mprotect`/W^X).
4. **Indireção em Automação de Sistema**: A camada de isolamento forçado do WASI dificulta operações naturais de administração de sistema (como pipes diretos de processos do SO, sinais de processo e acesso síncrono a terminais POSIX/Windows).

Diante dessas evidências, formaliza-se a evolução do Aipo rumo a um patamar de eficiência equivalente ao da **linguagem Lua** — universalmente reconhecida por sua inicialização sub-milissegundo, binário minúsculo (~250 KB a 500 KB) e facilidade de embutimento em motores de jogos e microcontroladores.

## 2. A Decisão: Arquitetura Dual-Track

Para acomodar tanto a portabilidade web quanto a performance enxuta de sistemas embarcados e scripts de terminal, o Aipo estabelece uma estratégia **Dual-Track**:

```
                  ┌────────────────────────────────────────┐
                  │             Código Aipo                │
                  │   (Frontend Canônico: Lexer / Sema)    │
                  └───────────────────┬────────────────────┘
                                      │
            ┌─────────────────────────┴─────────────────────────┐
            ▼                                                   ▼
 ┌──────────────────────┐                           ┌───────────────────────┐
 │     Track Web/Cloud  │                           │    Track Nativo/Embed │
 │   `aipo-wasm` (.wasm)│                           │  `aipo-bytecode` (.aibc)
 ├──────────────────────┤                           ├───────────────────────┤
 │ • Emissor: wasm-enc. │                           │ • VM: `aipo-vm`       │
 │ • Destino: Navegador,│                           │ • Destino: CLI Rápido,│
 │   Workers, Sandboxes │                           │   Shell, Jogos nativos│
 │ • Runner Wasmtime:   │                           │   e MCUs (`no_std`)   │
 │   Opcional (Feature) │                           │ • Sem dependências JIT│
 └──────────────────────┘                           └───────────────────────┘
```

### Esclarecimento Fundamental sobre o WASM

**Não abandonamos o WebAssembly.** O WebAssembly continua sendo o destino oficial para a Web e plataformas em nuvem que já oferecem seus próprios runtimes (navegadores, Deno, Bun, Cloudflare Workers). O crate `aipo-wasm` continuará gerando arquivos `.wasm` compactos via `wasm-encoder`.

**O que muda**: O interpretador JIT Wasmtime deixa de ser o executor mandatário da CLI desktop e passa a ser uma dependência condicional (*feature-gated*). A nossa própria máquina virtual (**`aipo-vm`**) assume a responsabilidade como motor de execução nativo de alta velocidade, pequeno porte e baixa pegada de memória.

## 3. Modelo de Evolução Progressiva em 3 Camadas

Para garantir que o mesmo núcleo atenda desde jogos em desktop até microcontroladores, a evolução da `aipo-vm` estrutura-se em **três camadas concêntricas**:

```
┌────────────────────────────────────────────────────────┐
│ Camada 3: Bare-Metal MCU (Horizonte Futuro)            │
│   • HAL de periféricos (GPIO, UART, I2C, Timers)       │
│   • `#![no_std]` estrito, zero dependência de SO       │
│   • Execução direta da Flash (XIP)                     │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Camada 2: System Shell (CLI Standalone)                │
│   • Builtins de processo (`spawn`, `pipe`, `env`, `fs`)│
│   • REPL interativo e pipes de dados `|>`              │
│   • Binário único estático (< 1 MB), boot < 2 ms       │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Camada 1: Host Scripting (Motor Central)               │
│   • `aipo-vm` como biblioteca C ABI (`libaipo.a`)      │
│   • Estado isolado por instância (`VmContext` reentrante│
│   • Zero dependência de SO: I/O via callbacks do host  │
│   • Modelo de memória compacto (16 bytes por valor)    │
│   • Gerenciamento por arenas com desalocação O(1)      │
└────────────────────────────────────────────────────────┘
```

- **Camada 1 (Host Scripting)**: A fundação universal. Um motor puro em Rust/C ABI sem dependências de SO. Todo I/O e ciclo de vida é controlado pelo hospedeiro através de uma interface de callbacks.
- **Camada 2 (System Shell)**: O motor da Camada 1 envelopado em um executável com primitivas de processo (`fork`, `exec`, pipes de kernel) e um REPL rápido para automação de infraestrutura.
- **Camada 3 (Bare-Metal MCU)**: O motor da Camada 1 configurado com `#![no_std]` e alocação estática, rodando diretamente em microcontroladores sem SO.

## 4. Comparativo Arquitetural: Aipo vs. Lua

Adotamos a arquitetura de **Lua 5.4** como referência padrão da indústria:

| Propriedade | Lua 5.4 (C) | Aipo Atual (Host Dev) | Aipo Perfil Nano / Shell (Meta) |
| :--- | :--- | :--- | :--- |
| **Tamanho do Binário** | ~280 KB (stripped) | ~20 a 30 MB (com Wasmtime) | **~350 KB a 550 KB** |
| **Tamanho da VM Isolada** | ~120 KB | ~1,5 MB (`aipo-vm` rlib) | **~50 KB a 90 KB** |
| **Tempo de Boot** | < 1 ms | 15 a 40 ms | **< 2 ms** |
| **Tamanho de `Value`** | 16 bytes (`TValue`) | 48 bytes (Enum Rust + `Rc`) | **16 bytes** (Tagged Union / NaN-boxing) |
| **Arquitetura de Bytecode**| Registradores Virtuais | Pilha Pura (Stack VM) | **Registradores Virtuais (32-bit u32)** |
| **Gerenciamento de Heap** | GC Tricolor Incremental | Alocador do SO (`Rc`/`RefCell`) | **Arenas Lineares (Desalocação O(1))** |
| **Ambiente Bare-Metal** | Totalmente portável (`no_std` C)| Depende de `std` e OS threads | **`#![no_std]` + `alloc` opcional** |

## 5. Delimitação Técnica do Perfil Reduzido (Embedded / Shell)

### O que é Sacrificado no Alvo Reduzido

1. **Diagnósticos Visuais Ricos**: Erros formatados com cores, sublinhados e sugestões contextuais são substituídos por tuplas enxutas `código:linha:coluna` (ex.: `E042:12:4`). As mensagens descritivas completas ficam no host de desenvolvimento.
2. **Tabelas de Normalização Unicode e Regex DFA**: Strings são tratadas como UTF-8 cru sem normalização avançada NFC em runtime, economizando mais de 500 KB de tabelas compiladas.
3. **Ponto Flutuante Obrigatório (`Float`)**: Em microcontroladores sem FPU, o suporte a `f64` é desativado via feature flag para evitar a inclusão de bibliotecas matemáticas pesadas em software.
4. **Alocação de Heap Irrestrita**: Substituição do alocador dinâmico do sistema por uma **Arena de Memória Linear de Tamanho Fixo** (ex.: 16 KB a 64 KB). Exceder a cota emite a falha segura `E_OUT_OF_MEMORY`.
5. **Concorrência Preemptiva Multi-Thread (`spawn`)**: No perfil nano, tarefas assíncronas tornam-se cooperativas em loop único ou erros de compilação.

### O que é Preservado (Onde o Aipo Supera Lua)

1. **Prevenção de Globais Invisíveis**: Escopo léxico estrito com `let` imutável por padrão e `var` restrito impede criação acidental de variáveis globais por erro de digitação.
2. **Tipos de Soma Fechados (`enum`) e `match` Exaustivo**: Enums e desestruturação possuem custo quase zero em runtime (apenas um índice numérico de tag), oferecendo segurança ausente em Lua.
3. **Operador de Pipe (`|>`)**: Ergonomia fluida tanto para manipulação de coleções quanto para pipelines de shell entre processos do sistema.
4. **Tratamento Explícito de Erros (`Result[T, E]`)**: Ausência de armadilhas de retornos nulos silenciosos ou exceções com overhead imprevisível.

## 7. Transição para Bytecode de Registradores Virtuais

A `aipo-vm` migrará do modelo de pilha pura para o modelo de **registradores virtuais com instruções fixas de 32 bits (`u32`)**:
- **Redução de Instruções**: Reduz entre 35% e 50% as instruções executadas para a mesma lógica em relação à máquina de pilha, cortando pela metade os ciclos de despacho de CPU.
- **Instruções Fixas de 4 Bytes**: Formato `iABC` (Opcode 7b, A 8b, B 9b, C 9b), `iABx` e `iAsBx`.
- **Execute-In-Place (XIP)**: Bytecode pode ser lido e executado diretamente da memória Flash do microcontrolador sem necessidade de ser copiado para a RAM.

## 8. Roteiro de Implementação em 4 Marcos

1. **Marco 1 — Desacoplamento e Enxugamento de Dependências**:
   - Feature flag `wasmtime-runner` no `crates/aipo-cli` (opcional).
   - Perfil `[profile.nano]` no workspace com `opt-level = "z"`, `lto = true`, `panic = "abort"`, `codegen-units = 1` e `strip = true`.
2. **Marco 2 — Compactação de `Value` e Arenas**:
   - Redução do layout de `Value` para 16 bytes.
   - Implementação do `ArenaAllocator` com reset O(1) e cota fixa.
3. **Marco 3 — Transição do Bytecode para Registradores**:
   - Especificação das instruções de 32 bits no `crates/aipo-bytecode`.
   - Laço de despacho direto no `crates/aipo-vm`.
4. **Marco 4 — CLI Shell e Suporte a C ABI**:
   - Binário `aipo-sh` com builtins de automação de sistema.
   - Validação da C ABI (`libaipo.a`) para embutimento em C/Rust.
