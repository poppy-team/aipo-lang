# ADP-014 — Perfil Embedded, Arquitetura Dual-Track (Wasm Web vs VM Nativa) e Roteiro de Evolução da `aipo-vm`

- **Status**: Proposto (Em Discussão e Desenho Arquitetural)
- **Data**: 2026-10-06
- **Decisores**: Raillen & Poppy Team
- **Fase**: Planejamento Arquitetural / Evolução de Runtimes

---

## 1. Contexto e Motivação

Na decisão arquitetural **ADP-013**, a linguagem Aipo adotou o formato WebAssembly (Wasm 2.0 / WASI) e o engine Wasmtime (JIT Cranelift) como substrato principal para unificar a execução e simplificar o caminho rumo ao auto-hospedamento (*self-hosting*).

Entretanto, medições práticas e a evolução dos objetivos de longo prazo da linguagem revelaram requisitos que um engine JIT pesado como o Wasmtime não consegue suprir:

1. **Pegada de Memória e Tamanho de Binário**: O Wasmtime, ao carregar o backend Cranelift, montadores x86/ARM, unwinding de pilha e alocador de registradores, adiciona mais de 25 MB ao binário final da CLI.
2. **Tempo de Inicialização (*Cold Start*) Incompatível com Shell**: Um script de terminal ou uma shell interativa exige inicialização imediata (< 2ms). A validação e compilação JIT de módulos Wasm impõe uma sobretaxa inicial perceptível (10ms a 50ms).
3. **Inviabilidade em Ambientes Embarcados (MCUs)**: Dispositivos sem MMU (ex.: Cortex-M, ESP32, RP2040) possuem apenas centenas de kilobytes de Flash e dezenas de kilobytes de RAM. Eles são incapazes de executar runtimes JIT complexos ou arquiteturas que exijam suporte a páginas executáveis em memória (`mprotect`/W^X).
4. **Indireção em Automação de Sistema**: A camada de isolamento forçado do WASI dificulta operações naturais de administração de sistema (como pipes diretos de processos do SO, sinais de processo e acesso síncrono a terminais POSIX/Windows).

Surge a necessidade de avaliar como o Aipo pode alcançar um patamar similar ao da **linguagem Lua** — universalmente consagrada por sua inicialização instantânea, binário minúsculo (~250 KB a 500 KB) e facilidade de embutimento em motores de jogos e microcontroladores.

## 2. A Decisão: Arquitetura Dual-Track

Para acomodar tanto a portabilidade web quanto a performance enxuta de sistemas embarcados e scripts de terminal, o Aipo estabelece uma estratégia **Dual-Track**:

```
                  ┌────────────────────────────────────────┐
                  │             Código Aipo                │
                  │   (Frontend Canônico: Lexer / Sema)    │
                  └───────────────────┬────────────────────┘
                                      │
            ┌─────────────────────────┴─────────────────────────┐
            ▼                                                   ▼
 ┌──────────────────────┐                           ┌───────────────────────┐
 │     Track Web/Cloud  │                           │    Track Nativo/Embed │
 │   `aipo-wasm` (.wasm)│                           │  `aipo-bytecode` (.aibc)
 ├──────────────────────┤                           ├───────────────────────┤
 │ • Emissor: wasm-enc. │                           │ • VM: `aipo-vm`       │
 │ • Destino: Navegador,│                           │ • Destino: CLI Rápido,│
 │   Workers, Sandboxes │                           │   Shell, Jogos nativos│
 │ • Runner Wasmtime:   │                           │   e MCUs (`no_std`)   │
 │   Opcional (Feature) │                           │ • Sem dependências JIT│
 └──────────────────────┘                           └───────────────────────┘
```

### Esclarecimento Fundamental sobre o WASM

**Não abandonamos o WebAssembly.** O WebAssembly continua sendo o destino de primeira classe para a Web e plataformas em nuvem que já oferecem seus próprios runtimes (navegadores, Deno, Bun, Cloudflare Workers). O crate `aipo-wasm` continuará gerando arquivos `.wasm` compactos via `wasm-encoder`.

**O que muda**: O interpretador JIT Wasmtime deixa de ser o executor mandatário da CLI desktop e passa a ser uma dependência condicional (*feature-gated*). A nossa própria máquina virtual (**`aipo-vm`**) assume a responsabilidade como motor de execução nativo de alta velocidade, pequeno porte e baixa pegada de memória.

## 3. Comparativo Arquitetural: Aipo vs. Lua

Para desenhar o perfil reduzido, adotamos a arquitetura de **Lua 5.4** como referência padrão da indústria:

| Propriedade | Lua 5.4 (C) | Aipo Atual (Host Dev) | Aipo Perfil Nano / Shell (Meta) |
| :--- | :--- | :--- | :--- |
| **Tamanho do Binário** | ~280 KB (stripped) | ~20 a 30 MB (com Wasmtime) | **~350 KB a 650 KB** |
| **Tamanho da VM Isolada** | ~120 KB | ~1,5 MB (`aipo-vm` rlib) | **~50 KB a 90 KB** |
| **Tempo de Boot** | < 1 ms | 15 a 40 ms | **< 2 ms** |
| **Tamanho de `Value`** | 16 bytes (TValue) | 48 bytes (Enum Rust + Rc) | **16 bytes** (Tagged Union / NaN-boxing) |
| **Gerenciamento de Heap** | GC Tricolor Incremental | Alocador do SO (`Rc`/`RefCell`) | **Arenas Lineares / GC Compacto** |
| **Pipeline de Compilação**| 1 passo (Single-pass AST-less)| 5 passos (Lexer→AST→HIR→Sema→IR)| **Fast-Path (AST→Bytecode Direto)** |
| **Ambiente Bare-Metal** | Totalmente portável (`no_std` C)| Depende de `std` e OS threads | **`#![no_std]` + `alloc` opcional** |

## 4. O que o Perfil Reduzido (Embedded / Shell) Sacrifica

Para que o Aipo consiga rodar em uma micro-VM com dezenas de kilobytes de RAM e Flash, certos recursos da linguagem precisam ser parametrizados ou excluídos desse perfil:

### Recursos Cortados no Alvo Reduzido

1. **Diagnósticos Visuais Ricos e Formatação de Erros**:
   - *No compilador completo*: Mensagens amigáveis, sublinhados coloridos, spans contextuais.
   - *No alvo reduzido*: Apenas tuplas simples `código:linha:coluna` (ex.: `E042:12:4`). As explicações e textos ficam no host de desenvolvimento.
2. **Tabelas de Normalização Unicode e Regex Pesadas**:
   - As tabelas de `unicode-normalization` e autômatos DFA de expressões regulares somam centenas de kilobytes no binário.
   - *No alvo reduzido*: Identificadores em ASCII e tratamento de texto como UTF-8 cru sem normalização avançada em tempo de execução.
3. **Ponto Flutuante Obrigatório (`Float`)**:
   - Em microcontroladores sem FPU de hardware, rotinas de software para IEEE-754 e conversão para string consomem precioso espaço de Flash.
   - *No alvo reduzido*: Tipos numéricos limitados a inteiros (`Int` 64-bit ou 32-bit fixo) e `Byte`. Ponto flutuante configurável via *feature flag*.
4. **Alocação de Heap Irrestrita**:
   - Substituição de alocações arbitrárias em heap global por uma **Arena de Memória de Tamanho Fixo** (ex.: buffer estático de 16 KB a 32 KB). Se o limite for excedido, o runtime emite uma falha segura de exaustão de cota (`E_OUT_OF_MEMORY`), sem corromper o sistema.
5. **Concorrência Preemptiva Multi-Thread (`spawn`)**:
   - Microcontroladores operam com loop de eventos cooperativo ou bare-metal com interrupções. No perfil nano, chamadas assíncronas concorrentes tornam-se erros de compilação ou rotinas cooperativas simples.

### Recursos Preservados (Onde o Aipo Supera Lua)

Mesmo no perfil mais restrito, o Aipo mantém os diferenciais fundamentais que o tornam superior a Lua para desenvolvimento moderno:

1. **Prevenção de Erros Globais**: Diferente de Lua, onde qualquer erro de digitação cria uma variável global invisível, Aipo exige declaração explícita (`let` imutável por padrão e `var` restrito).
2. **Tipos de Soma Fechados (`enum`) e `match` Exaustivo**: Enums e desestruturação possuem custo quase zero em runtime (apenas um índice numérico de tag no bytecode), oferecendo segurança inatingível em Lua.
3. **Operador de Pipe (`|>`)**: Ergonomia superior tanto para manipulação funcional de dados quanto para fluxos de shell e automação de comandos.
4. **Tratamento Explícito de Erros (`Result[T, E]`)**: Ausência de armadilhas de retornos nulos silenciosos ou exceções com overhead imprevisível.

## 5. Roteiro de Modernização da `aipo-vm`

Para alcançar essas metas sem quebrar a estabilidade da suíte de testes existente, o trabalho na branch `feat/embedded-vm-profile` seguirá quatro marcos:

### Marco 1: Desacoplamento e Enxugamento de Dependências
- Criar a feature flag `wasmtime-runner` no `crates/aipo-cli` (desligada por padrão no modo rápido).
- Configurar o perfil de compilação `[profile.nano]` no workspace com `opt-level = "z"`, `lto = true`, `panic = "abort"`, `codegen-units = 1` e `strip = true`.

### Marco 2: Compactação do Modelo de Valores (`Value`)
- Refatorar `crates/aipo-vm/src/value.rs` para reduzir o tamanho de `Value` de 48 bytes para 16 bytes.
- Investigar implementação de tagged union de duas palavras ou NaN-boxing para arquiteturas de 64 bits.
- Medir a redução de pressão sobre a cache L1 em benchmarks sintéticos.

### Marco 3: Desacoplamento `no_std` e Suporte a Arenas
- Parametrizar `aipo-bytecode` e o núcleo de `aipo-vm` com `#![no_std]` + `alloc`.
- Implementar alocador baseado em arena com reset instantâneo em bloco para execuções cíclicas e comandos de terminal.

### Marco 4: Fast-Path de Compilação para Modo Shell / REPL
- Criar um gerador de bytecode direto (`AST -> Bytecode`) que ignore transformações analíticas profundas quando um comando simples for digitado na linha de comando.
- Prototipar comandos básicos de automação de sistema operacional integrados como funções nativas da VM.
